# Owned GS dumps

Implemented for the pinned Windows PCSX2 v2.6.3 integration. Rebuild the native
emulator and TypeScript server, then restart/reconnect the MCP to discover:

| Tool | Contract |
|---|---|
| `pcsx2_gs_dump_start` | Queue a unique uncompressed `.gs` stream with VM identity, requested frames, native wall timeout and a hard byte ceiling. Does not resume. |
| `pcsx2_gs_dump_status` | Read/wait for this operation ID after reconnect. Verify a closed file's structure, size and hash; active/failed files remain unverified. |
| `pcsx2_gs_dump_cancel` | Cancel this ID only and await GS-thread cleanup. Does not pause/resume or stop a GUI-owned dump. |

The feature was motivated by Ryubara's
[GS dump extension](https://github.com/Ryubara/PCSX2-MCP/commit/3779165).
This adaptation keeps our protocol, operation ownership and v2.6.3 APIs; it does
not replace the DebugServer with that fork's v2.9.129 server.

## Usage

With a drawing program already running:

```json
{"frames":30,"timeout_ms":15000,"max_bytes":67108864}
```

Use the returned `operation_id` for status:

```json
{"operation_id":"<returned 32-character hex ID>","wait_ms":10000}
```

Start bounds: 1–300 requested video boundaries, 100–30000 ms wall lifetime,
1–256 MiB output ceiling (defaults: 1 frame, 15 seconds, 64 MiB).
The native dump format adds ending fields/boundaries; the actual number is
returned as `artifact.vsync_packets` and need not equal `frames_requested`.

A paused VM leaves the operation queued until explicitly resumed/advanced by
the caller. The native timeout continues while paused or disconnected. A status
wait timeout or request cancellation leaves the operation running until native
expiry or explicit cancellation. Timeout cleanup needs responsive CPU/GS threads;
an unresponsive host operation cannot be interrupted by this mechanism.

The file is written to `<instance-data-root>/mcp-gs-dumps/<operation_id>.gs`.
Names are generated by the MCP, existing files are refused, and no companion
screenshot is written. The stream contains PCSX2's embedded image capped at
640×480; the normal screenshot tool remains separate. The byte ceiling applies
to the entire uncompressed GS stream, including initial state and embedded image.
An insufficient ceiling produces a failed partial artifact rather than success.

One operation is retained until the next accepted start or server replacement;
completed files remain on disk. Save the response/ID before starting another.
Invalid/foreign IDs cannot cancel the retained operation. An existing GUI dump
or pending screenshot makes a start fail without replacing that work. Avoid
simultaneous GUI dump controls during MCP recording: changing native frame counts
can invalidate the requested minimum-frame criterion.

## State, identity and verification

Active states are `queued`, `recording`, `cancelling`. Terminal states are
`closed`, `cancelled`, `expired`, `invalidated`, `failed`. `cancelling` keeps
ownership until the GS callback confirms cleanup; another start is refused.

Native start guards PID, server session, execution epoch, ELF path and CRC.
ELF/VM reset and VM shutdown cancel the owned pending/active dump. GS work is
queued by the CPU thread, while renderer access and stream hooks run on the GS
thread. The integration preserves upstream renderer/dump object layouts.

`closed` requires the native end-of-frame condition and successful stream close.
It does not by itself assert artifact validation. The status tool then checks:

- Pinned uncompressed header and GS state version 9, bounded state/serial/image
  extents, packet types/lengths, field values and bounded FIFO read sizes.
- Complete packet boundaries and at least the requested VSync records.
- File size equal to native bytes submitted and below the requested ceiling.
- SHA256 and unchanged file metadata/operation during verification.

Parsing is bounded to 2 million packets and 15 seconds, with cancellation and
bounded read buffers. Corruption/truncation produces a tool error. The reported
`gs_crc` is the dump's disc/graphics identity; it is not substituted for the
separately captured `elf_crc`.

A GS dump contains graphics state/commands. It does not record audio, EE/IOP
execution, network traffic or a complete gameplay replay. Structural verification
does not promise pixel equivalence on every renderer or PCSX2 version.

## Validation recorded on 2026-10-21

- Windows MSVC build of PCSX2 v2.6.3 passed.
- 102 Node tests passed, including corrupt/truncated/oversized file rejection,
  ownership, identity, uncertain starts, cancellation and wait behavior.
- 8 live checks passed: real capture/verification, paused queue, conflicting
  start/foreign ID, reconnect/cancel, native expiry without video frames, hard
  byte limit, ELF reset invalidation and native GS replay with a rendered PNG.
- 11 existing automation live checks passed after the native integration changed.
- Pristine integration, upgrade from `75c147c`, reapplication and build checkout
  agree for all 18 integrated native source files.

The live reference was the local SMS/Jellyfin rendering ELF, with isolated data
roots and owned processes. An earlier development prototype failed a native
capture check; acceptance refers to the final integration preserving object
layouts, not that failed build. No failed prototype was published as accepted.

Receipts, streams and replay image are ignored local artifacts:
`release/gs-dump-validation-20261021-accepted/validation.json`,
`release/gs-dump-validation-20261021-accepted/replayed.png`,
`release/gs-dump-automation-regression-20261021/results.json` and
`release/gs-dump-integration-20261021-accepted/integration.json`.

Reproduce from `pcsx2-mcp-server`, with absolute paths and a fresh output:

```text
node test/gs-dump-live.mjs <PCSX2> <rendering-ELF> <configured-data-root> <new-output>
```

The fixture waits for the reference SMS startup before recording. Other homebrew
may need a different readiness condition. GUI-owned dump preservation, actual
disk-full/permission faults, GPU reset/backend switches and non-Windows runtimes
have implementation paths but no separate positive live acceptance here. No
physical PS2 debugging or playback/audio acceptance is claimed.
